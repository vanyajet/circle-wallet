# ADR-0008: Real-time через SSE поверх LISTEN/NOTIFY

**Статус:** Accepted

## Контекст
Статусы меняет worker, а соединение с браузером держит api (возможно, не один инстанс). Пользователь
должен видеть изменения сразу, без периодического polling.

## Решение
- Триггеры на изменяемых таблицах делают `pg_notify('app_events', '{"userId": …}')` в той же
  транзакции. По документации Postgres уведомление доставляется только после commit: событие
  о том, что потом откатилось, не уйдёт. Порядок соответствует порядку commit'ов, одинаковые
  уведомления внутри транзакции схлопываются, payload меньше 8000 байт (только id).
- Каждый инстанс api держит одно `LISTEN`-соединение (session pooler) и раздаёт события SSE-клиентам:
  `GET /users/:id/events`, `GET /events`.
- **Событие — это invalidate-сигнал.** Клиент перечитывает данные по REST (`invalidateQueries`),
  при каждом (пере)подключении делает полный refetch. Пропущенное событие безвредно, журнал для
  `Last-Event-ID` не нужен.
- Heartbeat каждые 15 с, `X-Accel-Buffering: no`, без compression. При обрыве `LISTEN` api
  переподключается и шлёт клиентам `resync`.

## Альтернативы

| Вариант | Плюсы | Минусы |
|---|---|---|
| Polling | Проще всего | Задержка, лишняя нагрузка, «тикающий» UI |
| **SSE + NOTIFY** (выбрано) | Нативный HTTP, авто-reconnect в браузере, pub/sub уже есть в Postgres | Долгоживущие соединения; NOTIFY не для огромного масштаба |
| WebSocket | Двунаправленный | Нам нужен только server → client; больше инфраструктуры |
| Supabase Realtime на фронте | Готовая инфраструктура | Фронт ходит в БД в обход бэкенда; без аутентификации это открытые данные |
| Redis/NATS pub/sub | Масштаб | Ещё один компонент; на нашем объёме не нужен |

## Последствия
- REST остаётся единственным источником данных для UI; SSE только ускоряет обновление.
- Чтобы масштабироваться, NOTIFY меняется на Redis/NATS без изменения клиентского контракта.
