# ADR-0010: Переводы по UID — off-chain проводка в леджере

**Статус:** Accepted

## Контекст
Пользователи платформы переводят средства друг другу, как переводы по UID на биржах (Bybit, Binance).
До этого единственный путь — вывод на deposit-адрес получателя:
1. on-chain перевод treasury → deposit wallet получателя;
2. депозит получателю;
3. sweep обратно на treasury.

Это два on-chain перевода, газ и минуты ожидания, после которых деньги возвращаются туда же, откуда ушли.
При omnibus ([ADR-0001](./0001-omnibus-custody-model.md)) средства пользователей уже лежат на кошельках
сервиса, а принадлежность определяет только леджер ([ADR-0003](./0003-double-entry-ledger.md)).

## Решение
- **Исполнение** — синхронно в API, одной транзакцией:
  - блокировка `USER_AVAILABLE` отправителя и получателя в детерминированном порядке;
  - проверка средств;
  - запись `internal_transfers`, сразу `COMPLETED`;
  - проводка `INTERNAL_TRANSFER`: дебет `USER_AVAILABLE(отправитель)`, кредит `USER_AVAILABLE(получатель)`.

  Ответ `201`. Circle, worker и блокчейн не участвуют.
- **Адресация:** UID — это id пользователя (UUID). Перед отправкой UI подтверждает получателя:
  `GET /transfer-recipients/:uid` возвращает только маскированное имя (`Iv***`), без балансов и адресов.
- **Идемпотентность** — как у выводов ([ADR-0009](./0009-idempotency-strategy.md)):
  - `Idempotency-Key` и хэш нормализованного тела;
  - `UNIQUE(sender_user_id, idempotency_key)`;
  - повторная проверка ключа после блокировки.
- **Вывод на deposit-адрес другого пользователя остаётся on-chain.** Это отдельный выбор пользователя
  (например, нужен txHash), перевод по UID его не заменяет.

## Альтернативы

### Исполнение
| Вариант | Плюсы | Минусы |
|---|---|---|
| **Off-chain проводка, синхронно, одна транзакция** (выбрано) | Мгновенно, без комиссии, атомарно: нет промежуточных состояний и окна для сбоя. Внешнего эффекта нет, поэтому не нужны ни outbox, ни worker | Некуда встроить асинхронные проверки (AML, ручной review) |
| On-chain: treasury → deposit-адрес получателя | Есть txHash | Газ, минуты ожидания, затем sweep гонит деньги обратно на treasury. Имеет смысл только в non-custodial модели |
| Двухфазно: HOLD → проверки в worker → SETTLE / RELEASE (как у выводов) | Есть место для лимитов, AML, заморозки, отмены | Больше состояний и задержка. Без таких проверок избыточно |

### Идентификатор получателя
| Вариант | Плюсы | Минусы |
|---|---|---|
| **UUID пользователя** (выбрано) | Без новой схемы. Пространство 2^122: опечатка почти наверняка даёт «не найден», а не чужого пользователя | Длинный, его не продиктовать. Публичный контракт привязан к PK |
| Короткий числовой UID (8–9 цифр + контрольная цифра) | Как у бирж, удобно диктовать | Новая колонка, backfill, генерация с ретраями при коллизии. Без контрольной цифры опечатка с ростом базы попадает в существующего пользователя |
| Последовательный номер | Просто | Перебор (enumeration), раскрывает число пользователей и темп роста |
| Никнейм | Человекочитаемо | Мутабелен: после переименования старый ник может занять другой, и перевод уйдёт не тому |

### Вывод на deposit-адрес другого пользователя
| Вариант | Плюсы | Минусы |
|---|---|---|
| **Оставить on-chain** (выбрано) | Поведение не меняется. У пользователя есть выбор: on-chain с txHash или мгновенный перевод по UID | Два on-chain перевода и газ, если выбран вывод |
| Запретить с подсказкой «используйте перевод по UID» | Честно, без лишнего газа | Мешает тем, кто не знает, что адрес наш |
| Автоматически превращать во внутренний перевод | Бесплатно и мгновенно | Нет txHash, меняется семантика withdrawal API |

## Последствия
- **Custody не меняется.** Деньги остаются там, где лежали: на treasury или на deposit-кошельке до sweep.
  Тождество Σ CUSTODY = Σ USER_* + Σ HOUSE сохраняется само, reconciliation с блокчейном не затрагивается.
  Если получатель выводит полученное раньше, чем завершится sweep отправителя, вывод ждёт ликвидности
  (`awaiting_liquidity`), как любой другой.
- **Встречные переводы не ловят deadlock.** Без порядка A→B блокирует A и ждёт B, а B→A — наоборот. Порядок
  задан на двух шагах (`lockAccounts`):
  1. счета создаются в порядке ключа счёта: незакоммиченная вставка нового счёта блокирует так же, как строка;
  2. строки блокируются в порядке `account_id` — в том же, в каком проводка обновляет балансы.

  Интеграционный тест проверяет оба шага; с наивным порядком он падает с `40P01`.
- **`status` допускает только `COMPLETED`.** Строка «PENDING без проводки» — состояние, которое не
  обрабатывает ни один код, поэтому CHECK её запрещает. Двухфазная схема расширит CHECK; API и история уже
  несут `status`, контракт не изменится.
- **SSE.** Общий `notify_app_event` читает `user_id`, а у перевода две стороны. Отдельный триггер сигналит
  обоим пользователям.
- **Перевод необратим.** Ошибку исправляет только новая, компенсирующая проводка: журнал append-only.
- **В проде дополнительно:**
  - отправитель — аутентифицированный пользователь, а не `:id` из URL; подтверждение 2FA;
  - rate limit на поиск получателя (защита от перебора);
  - лимиты и velocity-правила против layering, заморозка счетов — через двухфазную схему.
