# ADR-0005: Очередь задач в Postgres, отдельный worker, pg_cron как планировщик

**Статус:** Accepted

## Контекст
Работа с Circle асинхронна и ненадёжна: таймауты, неизвестный исход, вебхуки теряются и дублируются.
Нужны ретраи, восстановление после падений, периодическая сверка. Ни один сбой не должен терять
или удваивать деньги.

## Решение
- **Отдельный процесс worker** (та же кодовая база, другой entrypoint). api отвечает только за быстрые
  вещи и в Circle с мутациями не ходит.
- **Своя очередь в таблице `app.jobs`:**
  - задача ставится в **той же транзакции**, что и бизнес-изменение (transactional outbox);
  - захват через `FOR UPDATE SKIP LOCKED` с lease по часам БД, завершение с fencing по `locked_by`;
  - exponential backoff с jitter, `DEAD` после N попыток;
  - `dedupe_key` (partial unique index по активным задачам);
  - пробуждение по `NOTIFY` плюс опрос раз в секунду.
- **pg_cron как планировщик:** каждые 30–300 с вставляет периодические задачи `reconcile.*`
  с dedupe key. Выполняют их воркеры.
- **Graceful shutdown:** перестать брать задачи и дождаться текущих.

## Почему не фоновый цикл в процессе api
- Деплой или падение api останавливают фоновую обработку; баг в фоновом коде роняет HTTP.
- Тяжёлая сверка конкурирует с запросами за один event loop.
- При N репликах нужен leader election. Session-level advisory lock через pooler в transaction mode
  ненадёжен: lock привязан к серверному соединению.
- Вызов Circle прямо в HTTP-запросе заставляет обработчик разбираться с «неизвестным исходом».

## Почему pg_cron не исполнитель
- Вызов Circle требует API key и свежего RSA-OAEP шифротекста entity secret на каждый запрос.
  Секреты пришлось бы хранить в БД.
- `pg_net` из облачной БД не достучится до локального worker'а; бизнес-логику на SQL сложнее тестировать.
- Лимиты Supabase Cron: до 8 одновременных job, до 10 минут на job.

## Альтернативы

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Своя очередь в Postgres** (выбрано) | Задача ставится в той же транзакции, что и проводки; схема на виду в наших миграциях; ~200 строк | Свой код ретраев и lease (покрыт тестами) |
| graphile-worker / pg-boss | Проверенные библиотеки, cron, LISTEN | Своя схема вне наших миграций; transactional enqueue из нашей транзакции сложнее |
| SQS / RabbitMQ / Kafka + outbox relay | Масштаб, экосистема | Ещё одна инфраструктура и relay; overkill для задания |
| Temporal | Эталон durable workflows для саг | Отдельный кластер; overkill |
| Цикл в процессе api + advisory lock | Минимум кода | См. выше |

## Последствия
- Все side effects во внешних системах идемпотентны (ключ — id сущности), поэтому повтор задачи безопасен.
- Ожидание ликвидности — отдельный исход `reschedule`: попытки не расходуются.
- `DEAD`-задачи видны на `/ops` и сохраняют payload для повторного запуска.
