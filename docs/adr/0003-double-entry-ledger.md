# ADR-0003: Double-entry ledger, кешированные балансы, `numeric(78,0)`

**Статус:** Accepted

## Контекст
Приложение само ведёт балансы. Omnibus разводит «где лежат деньги» (кошельки) и «кому мы должны»
(пользователи). Нужны аудит, защита от двойного зачисления и double-spend, быстрые чтения балансов.

## Решение
- **Double-entry:**
  - счета `USER_AVAILABLE`, `USER_HELD` (обязательства), `CUSTODY` по кошельку (актив), `HOUSE` (equity),
    отдельно по каждому токену;
  - проводка состоит из записей с `direction ∈ {DEBIT, CREDIT}` и `amount > 0`; Σ debit = Σ credit.
- **Инварианты в БД:**
  - deferred constraint trigger проверяет баланс каждой проводки;
  - триггер запрещает `UPDATE`/`DELETE` (append-only);
  - `UNIQUE (kind, reference_id)` обеспечивает exactly-once;
  - `CHECK (balance >= 0)`.
- **Кешированный баланс** `ledger_accounts.balance` обновляется триггером на вставку записи в той же
  транзакции.
- **Суммы:** `numeric(78,0)` в минимальных единицах (78 цифр = uint256), в коде `bigint`, в API
  десятичные строки.
- **Снапшоты** откладываются (future work, pg_cron).

## Альтернативы

| Вариант | Плюсы | Минусы |
|---|---|---|
| Колонка `balance` у пользователя без журнала | Просто | Нет аудита («откуда эта сумма?»), легко потерять обновление, нельзя сверить |
| Баланс на лету как `SUM` по операциям | Нет кеша, нечему расходиться | Чтение O(n); при omnibus нет учёта custody по кошелькам |
| **Журнал + кешированный баланс** (выбрано) | Аудит, O(1) чтение, инварианты в БД | Кеш надо держать консистентным (решено триггером в той же транзакции) |
| Журнал + снапшоты без кеша | Хорошо масштабируется | Сложнее для текущих объёмов; можно добавить позже |
| Signed amounts вместо `direction` | Компактнее | Хуже читается: знак зависит от нормальной стороны счёта |
| `numeric(20,6)` / `bigint` / `float` | Компактнее | Не обобщается на 18-decimal токены; `bigint` (int8) переполняется на 18 decimals; float недопустим для денег |

## Последствия
- Ошибку можно исправить только новой проводкой: история неизменяема.
- Записи одной проводки вставляются в порядке `account_id`, чтобы избежать deadlock.
- Ops-проверка глобального тождества: Σ CUSTODY = Σ USER_* + Σ HOUSE по каждому токену.
