# ADR-0006: Inbox для вебхуков и проверка подписи

**Статус:** Accepted

## Контекст
Circle доставляет вебхуки at-least-once, без гарантии порядка, ждёт ответ около 5 секунд и повторяет
при не-2xx. Подпись — ECDSA P-256 (SHA-256) от сырого тела. Публичный ключ берётся по
`X-Circle-Key-Id`. URL подписки валидируется HEAD-запросом.

## Решение
- `HEAD /webhooks/circle` отвечает `200`.
- `POST /webhooks/circle` с `express.raw()` только на этом роуте:
  1. проверка подписи (ключ из `GET {CIRCLE_BASE_URL}/v2/notifications/publicKey/{keyId}`,
     кеш по keyId);
  2. валидация конверта;
  3. `webhooks.test` → `200` без эффектов;
  4. в одной транзакции `INSERT … ON CONFLICT (notification_id) DO NOTHING` и задача
     `webhook.process` → `200`.
- Неверная подпись → `401`. Ключ получить не удалось → `503`, чтобы Circle повторил.
- Обработка в worker: монотонная state machine, row lock, эффекты в леджере только на переходах.

## Альтернативы

| Вариант | Плюсы | Минусы |
|---|---|---|
| Обработка синхронно в HTTP-запросе | Меньше кода, ниже задержка | Риск таймаута; ошибка нашей логики превращается в ретраи Circle, у которых недокументированный лимит |
| **Inbox + async worker** (выбрано) | Мгновенный ack; сырой payload сохранён для аудита и replay; ретраи под нашим контролем | +1 таблица и задача; задержка равна латентности очереди (мс благодаря NOTIFY) |
| Только polling, без вебхуков | Не нужен публичный URL | Задержка; лишняя нагрузка на rate limit Circle |

## Последствия
- Dedupe идёт по `notificationId`, а **не** по id транзакции. В примере Circle arc-fintech dedupe по
  id транзакции отбрасывает `COMPLETE` после `CONFIRMED` как дубликат, у нас такой ошибки нет.
- Вебхук — триггер, но не единственный источник: reconciliation догоняет пропущенное.
- Проверка IP-адресов Circle — возможный defense in depth (не реализовано, подписи достаточно).
