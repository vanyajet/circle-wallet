# ADR-0009: Сквозная стратегия идемпотентности

**Статус:** Accepted

## Контекст
Повторы возникают на каждом звене: двойной клик и ретраи клиента, ретраи наших задач после падения,
повторная доставка вебхуков, повторное применение событий из reconciliation.

## Решение

| Звено | Механизм |
|---|---|
| Клиент → API | `Idempotency-Key` (UUID) + SHA-256 тела; `UNIQUE(user_id, idempotency_key)`. Тот же ключ с тем же телом → тот же ответ; с другим телом → `409 IDEMPOTENCY_KEY_REUSED` |
| Worker → Circle | `idempotencyKey` = id нашей сущности (детерминирован, переживает рестарты). `entitySecretCiphertext` новый на каждый запрос (повтор запрещён Circle, код `156004`). `refId` = `withdrawal:<id>` / `sweep:<id>` для поиска транзакции, если ответ потерялся |
| Circle → API | PK `notification_id` в inbox |
| Применение событий | Upsert по `circle_transaction_id`, монотонные статусы, row lock |
| Леджер | `UNIQUE(kind, reference_id)`: каждая проводка возможна ровно один раз |
| Очередь | `dedupe_key` по активным задачам, fencing по `locked_by` |

## Альтернативы
- Случайный `idempotencyKey` на каждую попытку: ретрай после неизвестного исхода создаёт второй
  перевод. Отвергнуто.
- Идемпотентность только на уровне API: не защищает от повторов внутри системы. Отвергнуто.

## Последствия
- При `156020` («use a new idempotency key») резерв **не** освобождается: сначала ищем транзакцию по
  `refId`, при неудаче задача уходит в `DEAD` для ручного разбора.
- Тело запроса для одного ключа никогда не меняется.
