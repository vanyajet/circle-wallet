# Заметки к обсуждению решения

Короткие ответы на вопросы, которые вероятнее всего зададут. Подробности — в [design-doc](design-doc.md) и [ADR](adr).

---

## Модель хранения и деньги

**Почему omnibus, а не кошелёк на пользователя?**
- Так устроены реальные кастодиальные кошельки и биржи:
  - ликвидность общая, и вывод не упирается в баланс одного адреса;
  - исходящие переводы идут из одной контролируемой точки;
  - модель готова к hot/cold-разделению.
- Цена: нужны sweep, классификация входящих на treasury и учёт ликвидности. Всё это реализовано ([ADR-0001](adr/0001-omnibus-custody-model.md)).

**Зачем double-entry, если есть баланс в Circle?**
- Circle знает, сколько лежит на адресе, но не знает, кому эти деньги принадлежат. В omnibus это разные вещи.
- Леджер разводит две стороны:
  - **custody** — где лежат деньги (актив по каждому кошельку);
  - **обязательства** — кому мы должны: `USER_AVAILABLE`, `USER_HELD`, `HOUSE`.
- Тождество Σ CUSTODY = Σ обязательств проверяется на `/ops`.

**Какие инварианты гарантирует БД, а не код?**
1. Проводка сбалансирована: deferred constraint trigger на commit.
2. Журнал append-only: триггер запрещает UPDATE/DELETE.
3. Exactly-once: `UNIQUE(kind, reference_id)`, так что депозит физически нельзя зачислить дважды.
4. `CHECK (balance >= 0)` — последняя линия защиты от double-spend.

**Как защищён вывод от double-spend?**
- `SELECT … FOR UPDATE` счёта `USER_AVAILABLE` сериализует параллельные выводы.
- Hold-проводка (available → held) делается в той же транзакции.
- `CHECK ≥ 0` страхует на случай бага.
- Это покрыто тестом: 6 параллельных выводов по 3 USDC с баланса 10 → ровно 3 проходят.

**Как устроены переводы по UID?**
- При omnibus принадлежность средств определяет только леджер. Поэтому перевод — одна проводка `USER_AVAILABLE(A) → USER_AVAILABLE(B)` в одной транзакции с записью перевода. Circle, worker и блокчейн не участвуют, custody не меняется: мгновенно и без газа ([ADR-0010](adr/0010-internal-transfers-off-chain.md)).
- Внешнего эффекта нет, поэтому нет ни outbox-задачи, ни промежуточных статусов: перевод сразу `COMPLETED`.
- **Deadlock встречных переводов** (A→B и B→A одновременно): оба счёта блокируются в порядке `account_id`, а новые счета создаются в порядке ключа. Тест проверяет оба шага; с наивной блокировкой «сначала свой счёт» большинство встречных переводов падает с `40P01` (в прогоне — 16 из 20).
- Идемпотентность и double-spend — как у выводов: `Idempotency-Key` + хэш тела, `FOR UPDATE`, `CHECK ≥ 0`.
- В проде: двухфазная схема (hold → лимиты/AML → settle), короткий UID с контрольной цифрой, 2FA и rate limit на поиск получателя.

**Почему `numeric(78,0)` и `bigint`?**
- 78 цифр вмещают uint256, поэтому модель подходит для любого ERC-20, включая 18-decimal.
- `float` недопустим для денег.
- `int8` переполняется на 18 decimals.
- В API суммы передаются десятичными строками, как у Circle. Парсинг строгий: лишняя точность — ошибка, а не округление.

**Кто платит газ?**
- Все кошельки — SCA, газ спонсирует Circle Gas Station (дефолтная политика тестнета).
- EOA (тип по умолчанию у Circle) требовал бы ETH на каждом deposit-кошельке. Публичный фаусет ETH не даёт.
- На живом прогоне ленивый деплой SCA при первом sweep прошёл за счёт Gas Station ([ADR-0002](adr/0002-sca-wallets-gas-station.md)).

## Sweep и treasury

**Когда и сколько сметаем?**
- Только после `COMPLETE` депозита: до него возможен reorg.
- Сумма берётся из леджера (CUSTODY кошелька), а не из on-chain баланса. Так не сметаем незафинализированное и не трогаем спам-токены.
- Мелочь ниже порога `SWEEP_MIN_AMOUNT` не сметаем, чтобы не тратить газ.
- На каждую пару «кошелёк + токен» не больше одного активного sweep (partial unique index).

**Как не перепутать ногу sweep на treasury с внешним пополнением?**
- Sweep проводится по своей outbound-транзакции, а входящая нога на treasury без проводок только классифицируется.
- Порядок сопоставления: Circle id → `refId` из REST → `txHash`. Поступление с нашего deposit-адреса никогда не уходит в house.
- При сомнении ждём или ставим `UNCLASSIFIED`. Учтённая ликвидность ниже реальной — это безопасно.
- **На живом прогоне** у ног sweep оказались **разные** Circle id, а `refId` во входящей ноге не было. Сработало сопоставление по `txHash`.

**А если treasury пуст?**
- Вывод не падает: он ждёт в статусе «ждёт ликвидности», попытки на ожидании не расходуются.
- Уходит, как только завершится sweep или придёт house float. Ликвидность = CUSTODY treasury − выводы в пути, вычисляется под блокировкой.

## Надёжность

**Что если Circle не ответил на создание перевода?**
- Исход неизвестен, поэтому вывод остаётся `SUBMITTING`, а резерв держится.
- Повтор сначала ищет транзакцию по `refId`, затем повторяет запрос с **тем же** `idempotencyKey` (это id вывода). Ciphertext при этом новый: Circle запрещает повторять ciphertext.
- 4xx на **повторную** отправку резерв не освобождает: первый запрос мог создать перевод. Этот баг нашли на ревью и исправили.

**Вебхуки потерялись или пришли не по порядку?**
- **Inbox:** проверить подпись → записать (dedupe по `notificationId`) → `200`.
- **Порядок:** state machine монотонна. Состояния `CLEARED` и `QUEUED` на одном уровне: на живом прогоне их порядок действительно плавал. Терминальное состояние не меняется.
- **Потери:** reconciliation по pg_cron опрашивает незавершённые операции и сканирует входящие. Корректность от вебхуков не зависит.

**Почему отдельный worker и своя очередь в Postgres?**
- **Transactional outbox:** задача ставится в одной транзакции с проводками.
- **Захват** через `SKIP LOCKED` и lease; fencing по паре «воркер + номер попытки».
- **Падение воркера** ничего не теряет: lease истекает, и задачу подхватывает другой.
- **Альтернативы** — graphile-worker/pg-boss, SQS/Kafka + outbox relay, Temporal. Аргументы в [ADR-0005](adr/0005-postgres-job-queue-separate-worker.md).

**Зачем pg_cron, если есть worker?**
- pg_cron — **планировщик**: ставит периодические задачи. Один планировщик на любое число воркеров, выбор лидера не нужен.
- **Исполнителем** он быть не может: вызов Circle требует секретов и RSA-шифрования на каждый запрос.

**Как SSE работает между процессами?**
- Триггеры делают `NOTIFY` в той же транзакции, и уведомление доставляется только после commit. api держит `LISTEN` и раздаёт SSE.
- Событие — invalidate-сигнал, данные клиент берёт по REST. Пропуск события безвреден.
- При обрыве LISTEN-соединения клиенты получают `resync`.

**Почему не supabase-js?**
- Каждый вызов supabase-js — отдельная HTTP-транзакция: нет `BEGIN…COMMIT`, `SKIP LOCKED` и `LISTEN`.
- `numeric` приходит как JSON number, и точность теряется.
- Supabase используется как managed Postgres с CLI для миграций и pg_cron; схема `app` закрыта от PostgREST, RLS включён ([ADR-0004](adr/0004-supabase-as-managed-postgres-kysely.md)).

**Почему свой клиент Circle, а не SDK?**
В SDK 10.8.1:
- нет таймаутов и ретраев;
- молча подставляется случайный `idempotencyKey`, и ретрай создаёт второй перевод;
- нет фильтра `refId`;
- `STUCK` считается терминальным.

Свой клиент строит все URL строго от `CIRCLE_BASE_URL` (работает с моком), валидирует ответы через zod и классифицирует ошибки по принципу «могли ли деньги уйти» ([ADR-0007](adr/0007-own-circle-http-client.md)).

## Безопасность
- Подпись каждого вебхука проверяется (ECDSA P-256 по сырому телу); ключ берётся через `CIRCLE_BASE_URL` и кешируется.
- `keyId`, не похожий на UUID, к Circle не идёт; неизвестные ключи кешируются как отсутствующие — защита от флуда, который съел бы rate limit.
- Секреты живут только в env, в логах они маскируются; recovery file хранится вне репозитория.
- Запрещены выводы на нулевой адрес, на контракт токена (USDC-контракт в denylist Circle), на treasury и на собственный deposit-адрес.
- Аутентификации нет по ТЗ. Для прода: authN/authZ, rate limiting, AML-скоринг адресов, отдельная защита `/ops`.

## Что показало ревью
Два независимых ревьюера проверили денежный код, найденное исправлено и покрыто тестами:
- **Главный баг:** 4xx на повторную отправку освобождал резерв, хотя перевод мог уже уйти (потенциальный double-spend).
- **Ответ Circle в обход state machine:** терминальное состояние из ответа на повтор могло «заморозить» вывод.
- **Reconcile starvation:** «застрявшие» строки вытесняли остальные. Исправлено ротацией по `last_reconciled_at`.
- **Fencing очереди:** раньше смотрел только на `locked_by`, теперь и на номер попытки. Время в очереди считается по часам БД.
- **Пробуждение задач:** раньше будило и выводы на backoff, что давало шторм ретраев; теперь будит только ждущие ликвидности.

## Проверено на живом Circle (BASE-SEPOLIA)
1. House float: фаусет → treasury → `HOUSE_FUNDING`.
2. Депозиты USDC и EURC: `CONFIRMED` → примерно 230 с → `COMPLETE` → зачисление.
3. Sweep обоих токенов с ленивым деплоем SCA → `COMPLETE` → ноги на treasury классифицированы как `SWEEP`.
4. Вывод Alice → Bob: `SETTLE`. Bob получил депозит, его средства тоже сметены.
5. Вывод через UI: «В очереди» → INITIATED → SENT → CONFIRMED → примерно 240 с → «Выполнен». Всё обновлялось через SSE, без перезагрузки.
6. Тождество леджера сходится; on-chain баланс treasury совпадает с CUSTODY.

## Что сделал бы дальше (prod)
- **Throughput:** пул hot wallets, авто-accelerate для `STUCK`.
- **Переводы и учёт:** двухфазные переводы по UID с лимитами и AML, комиссии, учёт газа.
- **Масштаб данных:** снапшоты балансов через pg_cron, партиционирование `ledger_entries`.
- **Инфраструктура:** Redis/NATS вместо NOTIFY на большом масштабе; закреплённый CA Supabase.
- **Наблюдаемость:** метрики и алерты на DEAD-задачи, `UNCLASSIFIED`-поступления и расхождения сверки.
